# 排队消息自动接续修复

## 目标

上一轮正常完成后，由服务端继续发送队首消息；网页关闭或手机休眠时也应生效。中断、失败或送达不明时继续阻止自动发送。

## 步骤

1. 在服务端队列与 Codex 状态读取的交界处复现：实时状态已空闲，但本地历史仍保留旧的进行中轮次。
2. 确认造成阻塞的状态来源，只在有权威完成信息时解除队列屏障。
3. 增加回归测试，覆盖正常完成、未完成和重复唤醒。
4. 运行相关测试与构建，检查差异，记录版本并提交本地 Git。

## 根因

排队服务先读取实时的空闲状态，之后又调用常规的完整历史读取。常规读取在轮次已结束时优先返回磁盘历史；Windows 的磁盘记录可能仍把该轮标为进行中，导致队列反复等待。队列校验现直接读取实时引擎的完整轮次；运行时未加载时先恢复会话，无法确认完成则保持排队。

## 二次排查：重启后仍不自动发送

分类：修复 / PATCH。恢复原有后台排队发送，不增加新能力。

现场：Windows 后端使用 Python 3.10.11。截图对应的消息仍为 pending，未暂停、未编辑、无发送尝试、无定时发送限制。既有回归只覆盖直接调用 advance 和后台首次立即发送，未覆盖等待超时后的长期运行。

执行步骤：

1. 用只读队列数据及最后轮次状态确认现场，保留用户消息不手动发送。
2. 在真实后台循环中复现空闲超时后退出，以及完成通知/定时复查不能继续发送。
3. 修复 Python 3.10 的异步超时捕获，验证正常完成可接续、取消仍能结束后台任务。
4. 执行后端测试和必要构建，记录版本并本地提交，不推送。
5. 在独立后台任务中安排当前回复结束后的服务重启，核实更新后的健康状态和排队投递；无法取得投递证据时如实说明。

确认的根因：Python 3.10 的 asyncio.TimeoutError 不等同于内置 TimeoutError。后台循环使用内置类型捕获 asyncio.wait_for 的 15 秒定时超时，导致第一次空闲超时即终止；监听器仍收到完成通知，但已经没有消费者执行发送。网页和后端健康接口正常并不能证明队列工作线程仍运行。

回归测试启动真实队列后台，缩短首次等待以稳定产生真实 asyncio 超时，再投递完成通知。修复前断言“队列任务已退出”失败，改为捕获 asyncio.TimeoutError 后通过，同时检查队列出队和后台任务正常取消。

验证结果：Python 3.10.11 下 205 项后端测试通过（4 项平台相关跳过）；另外使用原始 15 秒周期实际等待 16 秒后投递完成通知，队列仍存活且自动发送成功；pnpm build 通过。
