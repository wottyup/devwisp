# Android update download startup

## Requirement and classification

After detecting `0.133.3-dev.1`, tapping “下载更新” closes the confirmation but does not transfer data. The user supplied the phone address `10.126.126.2`; ADB connected at port 5555. Installed version is `0.133.2-dev.1` / 487 on Android 16. Preserve the installed app/data and unrelated server/web work; do not install another application or operate real chats.

Read-only inspection of the app's own pending update found task 120, 0 bytes and DownloadManager `STATUS_PAUSED` / `PAUSED_WAITING_TO_RETRY`. An app-context provider query through its existing debug connection reports underlying status 194, two connection failures and `failed to connect to /10.126.126.3 (port 4173) from /10.105.45.164 ... after 20000ms`. Thus the download was enqueued, but the system downloader cannot establish the connection that the app's update check can establish. Retrying only this task did not start transferring. A per-app VPN/routing difference is consistent with this evidence, but the VPN configuration itself was not inspected. Temporary diagnostic files and debugger forwards were removed and debugger threads resumed. No credentials were inspected or printed.

This is a PATCH correction to the existing update workflow. Target `0.133.4-dev.1`, Android versionCode `489`. Preserve application/signing identity and historical APKs; commit locally without pushing.

## Implementation steps

1. Download updater APKs with the app's own OkHttp client/UID instead of delegating their network requests to DownloadManager. Show immediate connection/progress state, stream off the UI thread and prevent overlapping jobs. Keep browser downloads separate.
2. Store partial/final APKs in an app-private update directory. Resume partial transfers with validated ranges, restart safely if a server ignores Range, bound bytes to the manifest size and verify SHA-256 before publishing the final APK. Serve only validated final APK filenames through a non-exported, read-only content provider with temporary URI grants for the system installer.
3. Keep the worker application-scoped so minimizing or destroying the Activity does not cancel it. Persist non-secret update metadata; if Android kills the process, resume the partial download when the app is reopened using the existing connection credentials. Retain cancel/minimize controls, explicit retry after errors and legacy downloaded-update handling. Do not promise OS-independent background execution after process death.
4. Add meaningful JVM transfer tests with local HTTP fixtures for authentication, truncation/range handling, digest/size failures and cancellation. Update both languages, the patch version and a concise changelog summary. Build/test offline and review cancellation/lifecycle transitions.
5. Verify/archive a new APK exclusively, confirm the preceding archive is unchanged and exercise actual update middleware selection/full download with fixture authentication. After the package is concrete and verified, use the user's earlier instruction to install directly on this phone to update the existing package in place; preserve its data and signing identity. The broken installed downloader cannot retrieve its own replacement over this route. Record actual phone-validation limits, clean temporary logs and commit only task-owned files.
